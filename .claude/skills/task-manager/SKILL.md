# Task Manager Skill

プロジェクトのタスクを「俯瞰用の `task.md` + 個別タスクファイル `tasks/{type}-{slug}.md`」のハイブリッドで管理するためのスキルです。

このスキルは「タスクをどう書くか/どう更新するか」の流儀を提供します。具体的な作業の進め方(設計→実装→テスト)はこのスキルの範囲外です。

---

## ディレクトリ構成

```
<project-root>/
├── task.md              # 全タスクの俯瞰一覧
└── tasks/
    ├── feat-xxx.md      # 個別タスクファイル(重い/複数セッション必要なもののみ)
    ├── fix-xxx.md
    ├── refactor-xxx.md
    └── chore-xxx.md
```

### 命名規約

- ファイル名: `{type}-{slug}.md`
- type: 以下の4つから選ぶ
  - `feat` … 新機能・新規追加
  - `fix` … バグ修正
  - `refactor` … 動作を変えないリファクタリング・改善
  - `chore` … インフラ・CI/CD・依存更新など雑務系
- slug: 英小文字とハイフン。簡潔に(3〜5語程度)
- 例: `feat-r2-migration.md`, `fix-email-reuse-after-failure.md`, `chore-cicd-pipeline.md`

### 個別ファイルに分けるかの判断基準

**分ける(`tasks/` に作る)**:
- 複数セッション(数時間以上)かかると見込まれる
- 設計判断・調査メモを残したい
- 受け入れ条件が複数ある
- 他タスクと依存関係がある

**分けない(`task.md` のチェックボックスのまま)**:
- 30分以内に終わる軽微なもの
- typo・設定値変更・コメント修正など

迷ったら分ける側に倒す。後から消すのは簡単。

## ワークフロー

### 1. 新規タスク追加

ユーザーが「〇〇というタスクを追加して」と言ったとき:

1. 上記の「分けるかの判断基準」で判断
2. **分ける場合**:
   - `templates/task-template.md` を参考に `tasks/{type}-{slug}.md` を作成
   - `task.md` の該当カテゴリに「リンク付きの1行」を追加
3. **分けない場合**:
   - `task.md` の該当カテゴリにチェックボックスで1行追加するだけ

`task.md` への追記例:

```markdown
## インフラ
- [ ] [R2移行](./tasks/feat-r2-migration.md)
- [ ] CORS設定の確認と制限
```

### 2. 作業中の進捗更新

ユーザーが「進捗を記録して」「今日やったことをまとめて」と言ったとき、または作業の区切りで自発的に:

1. 該当する `tasks/{type}-{slug}.md` を開く
2. `## 進捗ログ` セクションに、日付付きで1〜3行追記
3. 設計判断が発生していたら `## 設計メモ` にも追記
4. 受け入れ条件のうち満たしたものがあれば該当チェックボックスを `[x]` に

進捗ログの書き方:

```markdown
## 進捗ログ
- 2026-05-18: SDK選定。aws-sdk-js v3 を採用
- 2026-05-19: アップロード処理を src/storage/r2.ts に置き換え。ローカルfallbackは残す
```

「何をしたか」+「なぜそうしたか」を短く。長文にしない。

### 3. タスク完了処理

ユーザーが「このタスク完了」「終わったから閉じて」と言ったとき:

1. 個別ファイルがある場合:
   - すべての受け入れ条件チェックボックスを確認(満たしていないものがあれば指摘)
   - `## 進捗ログ` に完了行を追記: `- YYYY-MM-DD: 完了`
   - ファイル冒頭または末尾に `**Status: Done (YYYY-MM-DD)**` を明記
2. `task.md` の該当行を `[x]` に更新
3. ファイルは**削除しない**。完了記録として残す(後で参照できるように)

### 4. タスク一覧の確認

ユーザーが「今のタスク状況は?」「何が残ってる?」と言ったとき:

1. `task.md` を読む
2. 未完了のものを優先度順(高→中→低)で要約
3. 個別ファイルがあるタスクは、必要に応じて中身も確認して進捗を報告

## task.md の構成

カテゴリはプロジェクトに応じて変えるが、典型的には以下のように見出しで分ける:

```markdown
# Tasks

## インフラ
- [ ] [タスク名](./tasks/xxx.md) - 重要度

## バグ
- [ ] ...

## 機能追加
- [ ] ...

## セキュリティ
- [ ] ...

## UX
- [ ] ...

## ML / アルゴリズム
- [ ] ...

## 完了
<!-- 完了したタスクはここに移動してもよい(任意) -->
- [x] [タスク名](./tasks/xxx.md) - 2026-05-15
```

カテゴリ名はプロジェクトの既存の `task.md` に合わせる。新規に作る場合のみ上記をベースにする。

---

## 個別タスクファイルのテンプレート

新規作成時は `templates/task-template.md` をベースにする。最低限以下のセクションを含む:

- `# {type}: タイトル`
- `## 背景・目的`
- `## 受け入れ条件`(チェックボックス)
- `## 関連ファイル`
- `## 設計メモ`(任意、作業中に追記)
- `## 進捗ログ`
- `## 依存・ブロッカー`(任意)

詳細は `templates/task-template.md` を参照。実際に埋めた状態の例は `templates/example-task.md` にある。新規作成時はテンプレートと例の両方を確認すると、適切な粒度・記述量がつかめる。

---

## 重要な原則

- **既存のスタイルを尊重する**: ユーザーの `task.md` にすでにカテゴリ構成・記法のクセがあれば、それに合わせる。勝手に全面書き換えしない
- **小さな変更で済ませる**: 進捗更新で関係ないセクションに手を入れない
- **完了タスクのファイルを消さない**: 記録として残す
- **重要度を必ず付ける**: 高/中/低、または「重要度:高」など既存表記に合わせる
- **タスクの作業そのものはやらない**: このスキルはあくまで「タスク管理ファイルの操作」。実装作業を頼まれたら、それは別の話として受ける

---

## 既存の task.md からの移行

ユーザーが既存の `task.md`(1ファイル形式)をハイブリッド構成に移行したい場合:

1. 現在の `task.md` を読み、各タスクを「分ける/分けない」で仕分け
2. 「分ける」と判断したものについて、ユーザーに一覧を提示して確認
3. 承認後、`tasks/` ディレクトリと個別ファイルを作成
4. `task.md` を新形式(リンク付き俯瞰)に書き換える
5. **元のtask.md内容のバックアップを案内する**(`task.md.bak` として保存することを提案)

移行は1タスクずつ確認しながら進めるのが安全。一気にやらない。
